# 分布式锁组件（hgs-service-lock-framework）深度剖析

## 一、组件概述

`hgs-service-lock-framework` 是基于 Redisson 封装的分布式锁组件，为微服务环境提供声明式（注解）和编程式（命令/方法级别）两种加锁方式。组件通过 Spring 自动装配加载，依赖 `hgs-redisson-common-framework` 公共模块提供的锁名称解析基础设施。

### 1.1 模块依赖关系

```
hgs-service-lock-framework
├── hgs-redisson-common-framework  (锁名称解析、SpEL引擎、工厂)
├── spring-boot-starter-web        (optional)
└── redisson                       (由 common-framework 传递)
```

### 1.2 提供的三种使用方式

| 方式 | 入口 | 适用场景 |
|------|------|----------|
| 注解方式 | `@ServiceLock` 注解 | Service 层方法，推荐方式 |
| 命令模式 | `ServiceLockExecutor.execute()` | Lambda 包装业务逻辑 |
| 方法级别 | `ServiceLockExecutor.getLock()` | 手动 lock/unlock |

### 2.2 设计模式分析

| 设计模式 | 应用位置 | 作用 |
|----------|----------|------|
| **策略模式** | `LockType` + `ServiceLocker` 接口 + 4 种实现 | 不同锁类型可互换 |
| **工厂模式** | `ServiceLockFactory` | 根据 `LockType` 创建锁实例 |
| **模板方法** | `AbstractLockInfoHandle` | 定义锁名生成骨架，子类提供前缀 |
| **代理/装饰** | AOP 切面 `ServiceLockAspect` | 透明地为方法添加锁逻辑 |
| **命令模式** | `TaskRun` / `TaskCall` + `ServiceLockExecutor` | 将业务逻辑封装为可执行单元 |
| **缓存/享元** | `ManageLocker` | 锁实例在构造时一次性创建并缓存 |

## 三、核心组件详细分析

### 3.1 自动装配入口

`ServiceLockAutoConfiguration`

```java
public class ServiceLockAutoConfiguration {
    @Bean(LockInfoType.SERVICE_LOCK)
    public LockInfoHandle serviceLockInfoHandle() { ... }

    @Bean
    public ManageLocker manageLocker(RedissonClient redissonClient) { ... }

    @Bean
    public ServiceLockFactory serviceLockFactory(ManageLocker manageLocker) { ... }

    @Bean
    public ServiceLockAspect serviceLockAspect(...) { ... }

    @Bean
    public ServiceLockExecutor serviceLockTooL(...) { ... }
}
```

通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 注册：

```
com.hiddengemstore.config.ServiceLockAutoConfiguration
```

**Bean 装载链路：**

1. `ServiceLockInfoHandle` -- 锁名解析处理器，以 `service_lock` 为 Bean 名称注册
2. `ManageLocker` -- 持有 4 种锁实现的缓存，依赖 `RedissonClient`
3. `ServiceLockFactory` -- 根据 `LockType` 从 `ManageLocker` 获取锁
4. `ServiceLockAspect` -- AOP 切面，依赖 `LockInfoHandleFactory` + `ServiceLockFactory`
5. `ServiceLockExecutor` -- 编程式 API，依赖 `LockInfoHandleFactory` + `ServiceLockFactory`

### 3.2 锁名称解析体系

**(1) 接口层：`LockInfoHandle`**

```java
public interface LockInfoHandle {
    String getLockName(JoinPoint joinPoint, String lockName, String[] keys);  // AOP 使用
    String simpleGetLockName(String lockName, String[] keys);                 // 编程式使用
}
```

**(2) 抽象层：`AbstractLockInfoHandle`**

核心职责：
- **SpEL 表达式解析**：将 `#lockDataDto.id` 等表达式解析为运行时参数值
- **锁名拼接**：生成格式为 `{应用名}-{前缀}:{业务名}:{key1}:{key2}` 的锁名
- **方法参数发现**：通过 `ExtParameterNameDiscoverer` 获取方法参数名

锁名生成逻辑：

| 方法 | 格式 | 说明 |
|------|------|------|
| `getLockName()` | `{app}-{PREFIX}:{name}:{spelKeys}` | AOP 切面使用，支持 SpEL |
| `simpleGetLockName()` | `{app}-LOCK_DISTRIBUTE_ID:{name}:{keys}` | 编程式使用，直接拼接 |

SpEL 解析流程：

```
keys = {"#lockDataDto.id", "#lockDataDto.name"}
        │
        ▼
MethodBasedEvaluationContext(method, args)
        │
        ▼
SpelExpressionParser.parseExpression("#lockDataDto.id").getValue()
        │
        ▼
["123", "iPhone"]  →  拼接为 ":123:iPhone"
```

**(3) 实现层：`ServiceLockInfoHandle`**

```java
public class ServiceLockInfoHandle extends AbstractLockInfoHandle {
    private static final String LOCK_PREFIX_NAME = "SERVICE_LOCK";
    @Override
    protected String getLockPrefixName() { return LOCK_PREFIX_NAME; }
}
```

最终生成锁名示例：`hiddenGemStore-SERVICE_LOCK:order:12345`

**(4) 工厂层：`LockInfoHandleFactory`**

```java
public class LockInfoHandleFactory implements ApplicationContextAware {
    public LockInfoHandle getLockInfoHandle(String lockInfoType) {
        return applicationContext.getBean(lockInfoType, LockInfoHandle.class);
    }
}
```

通过 Spring `ApplicationContext` 按 Bean 名称动态获取，支持多种锁类型扩展（如幂等锁 `REPEAT_EXECUTE_LIMIT`）。

### 3.3 锁管理与工厂

**(1) `ManageLocker` -- 锁实例缓存**

```java
public class ManageLocker {
    private final Map<LockType, ServiceLocker> cacheLocker = new EnumMap<>(LockType.class);

    public ManageLocker(RedissonClient redissonClient) {
        cacheLocker.put(LockType.Reentrant, new RedissonReentrantLocker(redissonClient));
        cacheLocker.put(LockType.Fair,     new RedissonFairLocker(redissonClient));
        cacheLocker.put(LockType.Read,     new RedissonReadLocker(redissonClient));
        cacheLocker.put(LockType.Write,    new RedissonWriteLocker(redissonClient));
    }
}
```

使用 `EnumMap` 替代 `HashMap`，以枚举 ordinal 作为数组索引，查找复杂度 O(1)。

**(2) `ServiceLockFactory` -- 锁工厂**

```java
public ServiceLocker getLock(LockType lockType) {
    return switch (lockType) {
        case Fair   -> manageLocker.getFairLocker();
        case Write  -> manageLocker.getWriteLocker();
        case Read   -> manageLocker.getReadLocker();
        default     -> manageLocker.getReentrantLocker();
    };
}
```

使用 Java 14+ 增强 switch 表达式，简洁且无 fall-through 风险。

### 3.4 锁类型实现

**(1) `ServiceLocker` 接口定义**

```java
public interface ServiceLocker {
    RLock getLock(String lockKey);
    RLock lock(String lockKey);
    RLock lock(String lockKey, long leaseTime);
    RLock lock(String lockKey, long leaseTime, TimeUnit timeUnit);
    boolean tryLock(String lockKey, long waitTime, TimeUnit timeUnit);
    boolean tryLock(String lockKey, long waitTime, long leaseTime, TimeUnit timeUnit);
    void unlock(String lockKey);
    void unlock(RLock lock);
}
```

**(2) 四种锁实现对比**

| 实现类 | Redisson API | 特性 |
|--------|-------------|------|
| `RedissonReentrantLocker` | `redissonClient.getLock()` | 可重入，默认锁类型 |
| `RedissonFairLocker` | `redissonClient.getFairLock()` | 公平有序，FIFO 获取 |
| `RedissonReadLocker` | `redissonClient.getReadWriteLock().readLock()` | 读锁，共享 |
| `RedissonWriteLocker` | `redissonClient.getReadWriteLock().writeLock()` | 写锁，排他 |

所有实现遵循相同模式：
1. 通过 `RedissonClient` 获取对应的 `RLock` 实例
2. 委托调用 Redisson 的加锁/解锁方法
3. `tryLock` 捕获 `InterruptedException` 并返回 `false`

### 3.5 AOP 切面

`ServiceLockAspect`

```java
@Aspect
@Order(-10)  // 关键：优先级高于事务切面（默认 Integer.MAX_VALUE）
public class ServiceLockAspect {

    @Around("@annotation(serviceLock)")
    public Object around(ProceedingJoinPoint joinPoint, ServiceLock serviceLock) throws Throwable {
        // 1. 解析锁名
        // 2. 获取锁实例
        // 3. tryLock
        // 4. 成功 → 执行业务 → finally unlock
        // 5. 失败 → 自定义策略 / 默认快速失败 → 仍执行业务
    }
}
```

**执行流程：**

```
方法调用
  │
  ▼
@ServiceLock 注解拦截
  │
  ▼
解析锁名 (SpEL)
  │
  ▼
ServiceLockFactory.getLock(lockType)
  │
  ▼
lock.tryLock(lockName, waitTime, timeUnit)
  │
  ├── true ──→ joinPoint.proceed() ──→ finally: lock.unlock()
  │
  └── false ─→ 检查 customLockTimeoutStrategy
                  │
                  ├── 非空 ──→ 反射调用自定义方法
                  │
                  └── 空 ────→ lockTimeOutStrategy.handler()
                                │
                                └── FAIL: 抛 RuntimeException
```

**`@Order(-10)` 的重要性：**

此设置确保锁切面先于事务切面（`@Transactional`，默认 `@Order(Integer.MAX_VALUE)`）执行，保证锁的范围包裹整个事务。详见第六章"文档与代码一致性分析"。

### 3.6 `@ServiceLock` 注解

```java
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface ServiceLock {
    LockType lockType() default LockType.Reentrant;
    String name() default "";
    String[] keys();                                           // 必填
    long waitTime() default 10;
    TimeUnit timeUnit() default TimeUnit.SECONDS;
    LockTimeOutStrategy lockTimeOutStrategy() default LockTimeOutStrategy.FAIL;
    String customLockTimeoutStrategy() default "";
}
```

| 属性 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `lockType` | `LockType` | `Reentrant` | 锁类型 |
| `name` | `String` | `""` | 业务名称，作为锁名的一部分 |
| `keys` | `String[]` | **必填** | 锁标识，支持 SpEL |
| `waitTime` | `long` | `10` | 最大等待时间 |
| `timeUnit` | `TimeUnit` | `SECONDS` | 时间单位 |
| `lockTimeOutStrategy` | `LockTimeOutStrategy` | `FAIL` | 超时策略 |
| `customLockTimeoutStrategy` | `String` | `""` | 自定义策略方法名 |

### 3.7 编程式 API

`ServiceLockExecutor`

提供三种调用方式：

**(1) `execute()` -- 命令模式，无返回值**

```java
// 默认可重入锁，等待 20s
executor.execute(() -> businessLogic(), "order", new String[]{"123"});

// 指定锁类型和等待时间
executor.execute(LockType.Fair, () -> businessLogic(), "order", new String[]{"123"}, 10L);
```

**(2) `submit()` -- 命令模式，有返回值**

```java
Result result = executor.submit(() -> queryData(), "order", new String[]{"123"});
```

**(3) `getLock()` -- 方法级别，手动管理**

```java
RLock lock = executor.getLock(LockType.Reentrant, "order", new String[]{"123"});
lock.lock();
try {
    businessLogic();
} finally {
    lock.unlock();
}
```

### 3.8 超时处理策略

**(1) `LockTimeOutHandler` 接口**

```java
public interface LockTimeOutHandler {
    void handler(String lockName);
}
```

**(2) `LockTimeOutStrategy` 枚举**

```java
public enum LockTimeOutStrategy implements LockTimeOutHandler {
    FAIL() {
        @Override
        public void handler(String lockName) {
            throw new RuntimeException(String.format("锁 %s 获取超时", lockName));
        }
    }
}
```

当前仅支持 `FAIL`（快速失败）策略。可通过 `customLockTimeoutStrategy` 注解属性指定自定义处理方法，该方法通过反射调用，入参和出参与被加锁方法一致。

## 四、生命周期与状态管理

### 4.1 组件初始化时序

```
Spring Boot 启动
  │
  ▼
读取 META-INF/spring/...AutoConfiguration.imports
  │
  ▼
ServiceLockAutoConfiguration 被加载
  │
  ├── 1. ServiceLockInfoHandle 实例化
  ├── 2. ManageLocker 实例化（需要 RedissonClient 已就绪）
  │       └── 4 种 ServiceLocker 实现被创建并缓存
  ├── 3. ServiceLockFactory 实例化（注入 ManageLocker）
  ├── 4. ServiceLockAspect 实例化（注入 Factory + HandleFactory）
  └── 5. ServiceLockExecutor 实例化
```

### 4.2 执行流程图解

**注解方式执行流程**

```
用户调用被 @ServiceLock 标注的方法
        │
        ▼
ServiceLockAspect.around()  ← AOP 拦截
        │
        ├── 1. LockInfoHandleFactory.getLockInfoHandle("service_lock")
        │       └── 从 Spring 容器获取 ServiceLockInfoHandle 实例
        │
        ├── 2. lockInfoHandle.getLockName(joinPoint, name, keys)
        │       └── SpEL 解析 keys → 拼接完整锁名
        │           格式：{应用名}-SERVICE_LOCK:{name}:{key1}:{key2}
        │
        ├── 3. 从注解读取：lockType, waitTime, timeUnit
        │
        ├── 4. ServiceLockFactory.getLock(lockType)
        │       └── ManageLocker → 从缓存 Map 获取对应锁实例
        │
        ├── 5. lock.tryLock(lockName, timeUnit, waitTime)
        │       │
        │       ├── true  → 加锁成功
        │       │    ├── joinPoint.proceed()  ← 执行业务方法
        │       │    └── lock.unlock()        ← 解锁（finally）
        │       │
        │       └── false → 加锁失败
        │            ├── 有自定义策略 → 反射调用自定义方法
        │            └── 无自定义策略 → FAIL.handler() 抛异常
        │
        └── 返回结果
```

**命令方式执行流程**

```
serviceLockTool.execute(() -> businessLogic(), name, keys)
        │
        ├── 1. lockInfoHandle.simpleGetLockName(name, keys)
        │       └── 简单拼接锁名（不走 SpEL）
        │           格式：{应用名}-LOCK_DISTRIBUTE_ID:{name}:{key1}:{key2}
        │
        ├── 2. ServiceLockFactory.getLock(lockType)
        │
        ├── 3. lock.tryLock(lockName, TimeUnit.SECONDS, waitTime)
        │       │
        │       ├── true  → taskRun.run() + lock.unlock()
        │       └── false → FAIL.handler() 抛异常
        │
        └── 完成
```

**方法级别执行流程**

```
RLock lock = serviceLockTool.getLock(lockType, name, keys);
lock.lock();
try {
    // 业务逻辑
} finally {
    lock.unlock();
}
```

### 4.3 运行时状态

组件本身是**无状态**的：
- 锁实例在 `ManageLocker` 构造时一次性创建，运行时不再变更
- 锁的获取/释放完全委托给 Redisson，不维护本地锁状态
- `LockInfoHandleFactory` 通过 `ApplicationContext` 按需获取 Bean

### 4.4 Redisson 看门狗机制

当使用 `tryLock(waitTime, timeUnit)` 不指定 `leaseTime` 时，Redisson 的 Watchdog 机制生效：
- 默认锁过期时间 30s
- 每 10s（lockWatchdogTimeout / 3）自动续期
- 客户端宕机后锁自动释放

当指定 `leaseTime` 时，看门狗机制失效，锁到期后自动释放。

## 五、性能优化策略

### 5.1 `EnumMap` 替代 `HashMap`

`ManageLocker` 使用 `EnumMap<LockType, ServiceLocker>` 替代 `HashMap`：

- 内部以枚举 ordinal 为数组索引
- 查找时间复杂度 O(1)，无哈希计算开销
- 内存占用更小（数组而非链表/红黑树）

### 5.2 锁实例缓存

4 种锁实现在 `ManageLocker` 构造时一次性创建，后续直接从缓存获取，避免重复创建对象。

### 5.3 SpEL 表达式解析

每次注解方法调用都会解析 SpEL 表达式，存在一定开销。对于高频调用场景，可考虑缓存解析结果（当前未实现）。

### 5.4 `@Order(-10)` 避免无效事务

通过保证锁切面先于事务切面执行，避免了"事务已开启但未加锁"导致的数据竞争，减少了因数据不一致导致的重试开销。

## 七、错误处理机制

### 7.1 加锁失败处理

```
tryLock 返回 false
  │
  ├── 注解方式：
  │     ├── customLockTimeoutStrategy 非空 → 反射调用自定义方法
  │     └── 为空 → lockTimeOutStrategy.handler(lockName)
  │                 └── FAIL: 抛出 RuntimeException
  │
  └── 编程式方式（execute/submit）：
        └── 直接 FAIL: 抛出 RuntimeException
```

### 7.2 `InterruptedException` 处理

所有 `ServiceLocker` 实现中：

```java
try {
    return lock.tryLock(waitTime, timeUnit);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return false;  
}
```

**问题：** 捕获 `InterruptedException` 后恢复中断状态（`Thread.currentThread().interrupt()`），让上层逻辑感知线程被中断。**在AOP中通过判断加锁返回的状态，true执行业务，false选择失败处理策略。**

### 7.3 解锁异常

`unlock(String lockKey)` 方法会创建新的 `RLock` 实例来解锁：

```java
    public void unlock(String lockKey) {
        RLock lock = redissonClient.getLock(lockKey);
        // 判断当前线程是否持有锁,防止IllegalMonitorStateException异常
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
```

如果当前线程不是锁的持有者，Redisson 会抛出 `IllegalMonitorStateException`。切面中使用 `try-finally` 保证解锁，但在锁已过期（看门狗未续期）的情况下可能抛异常。

### 7.4 自定义策略反射调用异常

`handleCustomLockTimeoutStrategy` 中：
- `NoSuchMethodException` → 包装为 `RuntimeException` 抛出
- `IllegalAccessException` → 包装为 `RuntimeException` 抛出
- `InvocationTargetException` → 包装为 `RuntimeException` 抛出，原始异常作为 cause

## 八、组件交互关系

### 8.1 与 Redisson 的交互

```
ServiceLocker 实现 ──→ RedissonClient ──→ Redis Server
                         │
                         ├── getLock()        → RLock (可重入)
                         ├── getFairLock()    → RLock (公平)
                         └── getReadWriteLock() → RLock (读/写)
```

所有锁操作最终委托给 Redisson，由 Redisson 管理：
- Redis Lua 脚本保证原子性
- Watchdog 自动续期
- Pub/Sub 机制通知锁释放

### 8.2 与 Spring 事务的交互

```
请求进入
  │
  ▼
ServiceLockAspect (@Order(-10))  ←── 先执行
  │ lock
  ▼
TransactionalInterceptor (@Order(MAX_VALUE))  ←── 后执行
  │ begin transaction
  ▼
业务逻辑
  │
  ▼
commit/rollback
  │
  ▼
unlock
```

`@Order(-10)` 确保"先加锁，后开事务；先提交/回滚，后解锁"，保证事务的原子性在锁的保护范围内。

### 8.3 与幂等组件的共享

`LockInfoHandleFactory` 同时支持分布式锁和幂等两种处理器：

```java
// 分布式锁
lockInfoHandleFactory.getLockInfoHandle(LockInfoType.SERVICE_LOCK);
// 幂等控制
lockInfoHandleFactory.getLockInfoHandle(LockInfoType.REPEAT_EXECUTE_LIMIT);
```

两者共享 `AbstractLockInfoHandle` 基类和 `hgs-redisson-common-framework` 公共模块，仅前缀名称不同。

## 九、可维护性、可扩展性与复用性评估

### 9.1 可维护性

| 维度 | 评价 | 说明 |
|------|------|------|
| 代码结构 | **良好** | 分层清晰，职责单一 |

### 9.2 可扩展性

| 扩展点 | 方式 | 难度 |
|--------|------|------|
| 新增锁类型 | 实现 `ServiceLocker` 接口 + 注册到 `ManageLocker` | **低** |
| 新增锁名解析器 | 继承 `AbstractLockInfoHandle` + 注册 Spring Bean | **低** |
| 新增超时策略 | 扩展 `LockTimeOutStrategy` 枚举 或 使用 `customLockTimeoutStrategy` | **低** |
| 新增注解属性 | 修改 `@ServiceLock` 注解 + 切面逻辑 | **中** |

### 9.3 复用性

- `ServiceLocker` 接口抽象良好，可独立于注解使用
- `AbstractLockInfoHandle` 和 `LockInfoHandleFactory` 已被幂等组件复用
- `TaskRun` / `TaskCall` 函数式接口设计简洁，易于 Lambda 使用

### 9.4 改进建议

1. **SpEL 缓存**：对高频调用的注解方法，缓存 SpEL 解析结果以减少反射开销
2. **`submit` 方法可配置化**：当前 `submit` 硬编码 30s 等待时间和 `Reentrant` 锁类型，建议增加重载方法支持自定义

## 十、总结

`hgs-service-lock-framework` 是一个设计良好的分布式锁封装组件，核心优势在于：

1. **三种使用方式**覆盖了从声明式到编程式的完整场景
2. **策略模式 + 工厂模式**使锁类型可灵活扩展
3. **`@Order(-10)` 解决了锁与事务的顺序问题**，这是生产环境中的关键细节
4. **SpEL 支持**使锁的粒度可以精确到业务参数级别
5. **与幂等组件共享基础设施**，减少了重复代码
