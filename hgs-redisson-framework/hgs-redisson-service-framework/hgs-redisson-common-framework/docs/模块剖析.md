## 一、模块总览

### 1.1 模块定位

`hgs-redisson-common-framework` 是 `hgs-redisson-service-framework` 下的**公共基础模块**，本身不含业务逻辑，为上层模块提供 Redisson 客户端初始化、分布式锁名称解析、本地锁缓存等基础能力。

```
hgs-redisson-framework
  └─ hgs-redisson-service-framework（POM 聚合模块）
       ├─ hgs-redisson-common-framework      ← 本模块
       ├─ hgs-service-lock-framework          （分布式服务锁）
       ├─ hgs-repeat-execute-limit-framework  （防重复执行/幂等）
       └─ hgs-bloom-filter-framework          （布隆过滤器）
```

### 1.2 包结构

```
com.hiddengemstore
├── config/                         # 自动装配模块
│   ├── RedissonBaseProperties.java
│   └── RedissonCommonAutoConfiguration.java
├── constants/                      # 常量定义
│   └── LockInfoType.java
├── core/                           # 数据操作模块
│   └── RedissonDataHandle.java
├── locallock/                      # 本地锁缓存模块
│   └── LocalLockCache.java
└── lockinfo/                       # 锁名称解析模块
    ├── LockInfoHandle.java
    ├── AbstractLockInfoHandle.java
    ├── factory/
    │   └── LockInfoHandleFactory.java
    └── parser/                     # 参数名解析子模块
        ├── ExtParameterNameDiscoverer.java
        └── LocalVariableTableParameterNameDiscoverer.java
```

### 1.3 外部依赖

| 依赖 | 用途 |
|------|------|
| `hgs-common` | `SpringUtil`（应用前缀）、`Constant`（配置常量） |

## 二、自动装配模块 — config 包

### 2.1 RedissonCommonAutoConfiguration

自动装配入口，通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 注册。

**执行时机：**

```java
@AutoConfigureBefore(value = {RedissonAutoConfigurationV2.class, RedissonAutoConfiguration.class})
@EnableConfigurationProperties(RedissonBaseProperties.class)
public class RedissonCommonAutoConfiguration { ... }
```

在官方 Redisson 自动配置**之前**执行，拦截并替代默认的客户端创建逻辑。

**RedissonClient 创建流程：**

```
读取 RedisProperties（Spring Boot 内置）
  ↓
反射检测 isSsl() → 确定协议前缀 redis:// 或 rediss://
  ↓
配置单机模式: address + connectTimeout(1s) + database + password
  ↓
设置 threads(16) / nettyThreads(32)
  ↓
如果 corePoolSize + maximumPoolSize 同时配置 → 创建自定义线程池
  ↓
Redisson.create(config)
```

**SSL 兼容处理：**

```java
Method method = ReflectionUtils.findMethod(RedisProperties.class, "isSsl");
if (method != null && (Boolean)ReflectionUtils.invokeMethod(method, redisProperties)) {
    prefix = "rediss://";
}
```

使用反射兼容不同 Spring Boot 版本（`isSsl()` 在某些版本中不存在时安全跳过）。

**自定义线程池：**

```java
// 仅当 corePoolSize 和 maximumPoolSize 同时配置时才创建
if (Objects.nonNull(redissonBaseProperties.getCorePoolSize()) &&
        Objects.nonNull(redissonBaseProperties.getMaximumPoolSize())) {
    ThreadPoolExecutor threadPoolExecutor = new ThreadPoolExecutor(
            corePoolSize, maximumPoolSize, keepAliveTime, unit,
            new LinkedBlockingQueue<>(workQueueSize),
            r -> new Thread(Thread.currentThread().getThreadGroup(), r,
                    "redisson-thread-" + executeTaskThreadCount.getAndIncrement()));
    config.setExecutor(threadPoolExecutor);
}
```

- `executeTaskThreadCount` 为 `AtomicInteger`，保证线程名全局唯一
- `LinkedBlockingQueue(256)` 有界队列，防止任务堆积导致 OOM

### 2.2 RedissonBaseProperties

绑定前缀：`spring.redis.redisson`

| 属性 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `threads` | `Integer` | `16` | Redisson 工作线程池大小 |
| `nettyThreads` | `Integer` | `32` | Netty 线程池大小 |
| `corePoolSize` | `Integer` | `null` | 自定义线程池核心线程数（可选） |
| `maximumPoolSize` | `Integer` | `null` | 自定义线程池最大线程数（可选） |
| `keepAliveTime` | `long` | `30` | 线程空闲存活时间 |
| `unit` | `TimeUnit` | `SECONDS` | 空闲时间单位 |
| `workQueueSize` | `Integer` | `256` | 任务队列容量 |

配置示例：

```yaml
spring:
  redis:
    host: localhost
    port: 6379
    password: your_password
    database: 0
    redisson:
      threads: 16
      netty-threads: 32
      core-pool-size: 8
      maximum-pool-size: 32
      keep-alive-time: 30
      work-queue-size: 256
```

## 三、锁名称解析模块 — lockinfo 包

### 3.1 LockInfoHandle 接口

```java
public interface LockInfoHandle {
    // AOP 场景：通过 JoinPoint 解析 SpEL 表达式生成锁名
    String getLockName(JoinPoint joinPoint, String lockName, String[] keys);

    // 编程式场景：直接使用 key 字符串拼接
    String simpleGetLockName(String lockName, String[] keys);
}
```

| 方法 | 适用场景 | SpEL 支持 | 锁名格式 |
|------|---------|-----------|---------|
| `getLockName()` | AOP 切面 | 是 | `{应用前缀}-{锁类型前缀}:{lockName}:{key1}:{key2}` |
| `simpleGetLockName()` | 编程式调用 | 否 | `{应用前缀}-LOCK_DISTRIBUTE_ID:{lockName}:{key1}:{key2}` |

示例：`hmdp-SERVICE_LOCK:order_lock:12345`

### 3.2 AbstractLockInfoHandle 抽象实现

模板方法模式，子类只需实现 `getLockPrefixName()` 定义锁类型前缀。

**内部状态：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `LOCK_DISTRIBUTE_ID_NAME_PREFIX` | `String`（常量） | 编程式模式前缀 `"LOCK_DISTRIBUTE_ID"` |
| `nameDiscoverer` | `ExtParameterNameDiscoverer` | 参数名发现器 |
| `parser` | `SpelExpressionParser` | SpEL 解析器，线程安全 |

**`getLockName()` 生成流程：**

```
getLockName(joinPoint, lockName, keys)
  ↓
1. SpringUtil.getPrefixDistinctionName()  → 应用前缀（如 "hmdp"）
  ↓
2. getLockPrefixName()                    → 锁类型前缀（子类实现）
  ↓
3. getRelKey(joinPoint, keys)
   ├── getMethod(joinPoint)               → 获取目标方法（处理接口代理）
   └── getSpElKey(keys, method, args)     → 逐个解析 SpEL 表达式
  ↓
4. 拼接: "{prefix}-{lockPrefix}:{lockName}:{key1}:{key2}"
```

**接口代理处理：**

```java
private Method getMethod(JoinPoint joinPoint) {
    MethodSignature signature = (MethodSignature) joinPoint.getSignature();
    Method method = signature.getMethod();
    if (method.getDeclaringClass().isInterface()) {
        try {
            method = joinPoint.getTarget().getClass().getDeclaredMethod(
                    signature.getName(), method.getParameterTypes());
        } catch (Exception e) {
            log.error("get method error ", e);
        }
    }
    return method;
}
```

当目标方法声明在接口上时（JDK 动态代理），从实现类中获取真实方法以正确解析参数名。

### 3.3 SpEL 表达式解析流程

```java
private List<String> getSpElKey(String[] definitionKeys, Method method, Object[] parameterValues) {
    List<String> definitionKeyList = new ArrayList<>();
    for (String definitionKey : definitionKeys) {
        if (!ObjectUtils.isEmpty(definitionKey)) {
            EvaluationContext context = new MethodBasedEvaluationContext(null, method, parameterValues, nameDiscoverer);
            Object objKey = parser.parseExpression(definitionKey).getValue(context);
            definitionKeyList.add(ObjectUtils.nullSafeToString(objKey));
        }
    }
    return definitionKeyList;
}
```

支持的 SpEL 表达式形式：

| 表达式 | 说明 | 示例 |
|--------|------|------|
| `#userId` | 直接引用参数名 | `@ServiceLock(keys = "#userId")` |
| `#order.id` | 引用参数的属性 | `@ServiceLock(keys = "#order.id")` |
| `#p0` | 按位置引用 | `@ServiceLock(keys = "#p0")` |
| `#p0.name` | 按位置引用属性 | `@ServiceLock(keys = "#p0.name")` |

> `#userId` 和 `#order.id` 形式的解析依赖参数名发现器，需要 `LocalVariableTableParameterNameDiscoverer` 支持。详见[第四节](#四参数名解析模块--parser-包)。

### 3.4 LockInfoHandleFactory 工厂

```java
public class LockInfoHandleFactory implements ApplicationContextAware {
    private ApplicationContext applicationContext;

    public LockInfoHandle getLockInfoHandle(String lockInfoType) {
        return applicationContext.getBean(lockInfoType, LockInfoHandle.class);
    }
}
```

通过 `ApplicationContextAware` 获取 Spring 容器引用，运行时按 Bean 名称查找对应的 `LockInfoHandle` 实现。

**继承体系：**

```
LockInfoHandle (接口)
    ├── AbstractLockInfoHandle (抽象类，提供 SpEL 解析能力)
    │     ├── ServiceLockInfoHandle           Bean名: "service_lock"
    │     └── RepeatExecuteLimitInfoHandle    Bean名: "repeat_execute_limit"
    └── LockInfoHandleFactory (工厂，按 Bean 名称查找)
```

**扩展方式：** 新增锁类型只需：
1. 继承 `AbstractLockInfoHandle`，实现 `getLockPrefixName()`
2. 以 `@Bean` 注册到 Spring 容器

### 3.5 LockInfoType 常量

```java
public interface LockInfoType {
    String REPEAT_EXECUTE_LIMIT = "repeat_execute_limit";  // 防重复执行幂等
    String SERVICE_LOCK = "service_lock";                   // 分布式服务锁
}
```

同时作为 Bean 名称和锁类型标识使用。

### 3.6 设计模式分析

本模块主要运用了**模板方法模式 + 工厂模式**的组合。

**1. 模板方法模式（Template Method Pattern）** — 核心模式

`AbstractLockInfoHandle` 定义了锁名称生成的完整算法骨架，子类通过钩子方法提供差异化的参数值：

```java
// AbstractLockInfoHandle.java — 算法骨架固定
public String getLockName(JoinPoint joinPoint, String lockName, String[] keys) {
    return SpringUtil.getPrefixDistinctionName() + "-" +
            getLockPrefixName() +   // ← 钩子方法，由子类实现
            ":" + lockName + getRelKey(joinPoint, keys);
}
```

- **抽象类**：`AbstractLockInfoHandle` 定义固定流程（取应用前缀 → 拼锁类型前缀 → 解析 SpEL → 拼接 keys）
- **钩子方法**：`getLockPrefixName()` 由子类实现，返回不同的锁类型前缀字符串
- **具体子类**：`ServiceLockInfoHandle` 返回 `"SERVICE_LOCK"`，`RepeatExecuteLimitInfoHandle` 返回 `"REPEAT_EXECUTE_LIMIT"`

> **为什么不是策略模式？** 策略模式要求子类封装**不同的算法逻辑**（如快排 vs 归并）。而本模块的子类之间算法逻辑完全相同，唯一区别是 `getLockPrefixName()` 返回的常量值不同。这是典型的模板方法模式——算法骨架不变，只有某个步骤的参数由子类决定。

**2. 工厂模式（Factory Pattern）**

- `LockInfoHandleFactory` 通过 `ApplicationContextAware` 获取 Spring 容器
- 根据 `lockInfoType`（Bean 名称）运行时动态查找并返回对应的 `LockInfoHandle` 实现
- 避免在业务代码中硬编码具体类

```java
// 运行时根据 Bean 名称获取对应实现
LockInfoHandle lockInfoHandle = lockInfoHandleFactory.getLockInfoHandle(LockInfoType.SERVICE_LOCK);
```

**模式协作关系：**

```
调用方（如 ServiceLockAspect）
  ↓ 通过工厂获取实现
LockInfoHandleFactory.getLockInfoHandle("service_lock")   ← 工厂模式
  ↓ 返回具体子类实例
ServiceLockInfoHandle extends AbstractLockInfoHandle
  ↓ 调用模板方法
AbstractLockInfoHandle.getLockName(...)                    ← 模板方法模式
  ↓ 内部调用钩子
getLockPrefixName() → "SERVICE_LOCK"                      ← 子类提供参数
```

总结：核心是**模板方法模式**，通过**工厂模式**实现运行时选择具体子类。新增锁类型只需继承 `AbstractLockInfoHandle`，实现 `getLockPrefixName()` 返回新前缀，并注册为 Bean 即可，无需修改已有代码，符合开闭原则。

## 四、参数名解析模块 — parser 包

### 4.1 ExtParameterNameDiscoverer

```java
public class ExtParameterNameDiscoverer extends DefaultParameterNameDiscoverer {
    public ExtParameterNameDiscoverer() {
        super();
        if (!NativeDetector.inNativeImage()) {
            addDiscoverer(new LocalVariableTableParameterNameDiscoverer());
        }
    }
}
```

继承 Spring 的 `DefaultParameterNameDiscoverer`（支持 `-parameters` 编译），额外添加 `LocalVariableTableParameterNameDiscoverer` 作为兜底方案。GraalVM Native Image 环境下跳过。

**解析链路：**

```
AbstractLockInfoHandle 需要参数名
  ↓
ExtParameterNameDiscoverer
  ├── DefaultParameterNameDiscoverer  ← 优先：读取 -parameters 编译的类
  └── LocalVariableTableParameterNameDiscoverer  ← 兜底：读取 .class 字节码
```

### 4.2 LocalVariableTableParameterNameDiscoverer

通过 ASM 读取 `.class` 文件的 `LocalVariableTable` 属性提取参数名。Spring 6.1 已废弃此类，但 `#对象.属性` 形式的 SpEL 解析仍依赖它。

**核心流程：**

```
getParameterNames(method)
  ↓
BridgeMethodResolver.findBridgedMethod(method)  ← 处理泛型桥接方法
  ↓
parameterNamesCache.computeIfAbsent(declaringClass, this::inspectClass)
  ↓
inspectClass(clazz):
  ├── clazz.getResourceAsStream(classFileName)  ← 加载 .class 文件
  ├── new ClassReader(is)                       ← ASM 读取字节码
  └── classReader.accept(ParameterNameDiscoveringVisitor, 0)
```

**ASM 访问者体系：**

- **`ParameterNameDiscoveringVisitor`**（类级）：遍历所有方法，跳过 synthetic/bridge/`<clinit>`
- **`LocalVariableTableVisitor`**（方法级）：从局部变量表中匹配参数槽位索引，处理 `this` 隐式参数和 `long`/`double` 双槽位

**缓存机制：**

```java
private final Map<Class<?>, Map<Executable, String[]>> parameterNamesCache = new ConcurrentHashMap<>(32);
```

类级别缓存，每个类只解析一次。`ConcurrentHashMap` 保证并发安全，但无容量限制和过期策略。

## 五、本地锁缓存模块 — locallock 包

### 5.1 LocalLockCache

使用 Caffeine 缓存管理本地 `ReentrantLock` 实例，作为分布式锁的本地第一道防线。

**初始化（`@PostConstruct`）：**

```java
@Value("${durationTime:48}")
private Integer durationTime;

@PostConstruct
public void localLockCacheInit() {
    localLockCache = Caffeine.newBuilder()
            .expireAfterWrite(durationTime, TimeUnit.HOURS)
            .build();
}
```

**核心方法：**

```java
public ReentrantLock getLock(String lockKey, boolean fair) {
    return localLockCache.get(lockKey, key -> new ReentrantLock(fair));
}
```

| 参数 | 说明 |
|------|------|
| `lockKey` | 锁的唯一标识 |
| `fair` | `true` = 公平锁（FIFO），`false` = 非公平锁（性能更高） |

- 缓存命中时返回已有实例，未命中时创建并缓存
- `Caffeine.get()` 保证同一 key 只执行一次 `mappingFunction`
- 锁实例在写入后 48 小时（可配置）自动过期清理

## 六、数据操作模块 — core 包

### 6.1 RedissonDataHandle

封装 `RedissonClient.getBucket()` 的字符串缓存操作。

**API 清单：**

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `get(key)` | `String key` | `String` | 获取缓存值，不存在返回 `null` |
| `set(key, value)` | `String, String` | `void` | 设置永不过期的缓存 |
| `set(key, value, ttl, unit)` | `String, String, long, TimeUnit` | `void` | 设置带过期时间的缓存 |
| `getDuration(ttl, unit)` | `long, TimeUnit` | `Duration` | 时间单位转换 |

**`getDuration()` 支持的 TimeUnit：**

| TimeUnit | 转换方法 |
|----------|---------|
| `SECONDS`（default） | `Duration.ofSeconds()` |
| `MINUTES` | `Duration.ofMinutes()` |
| `HOURS` | `Duration.ofHours()` |
| `DAYS` | `Duration.ofDays()` |

> `MILLISECONDS`、`MICROSECONDS`、`NANOSECONDS` 缺失，走 default 会错误转为 `Duration.ofSeconds()`。

**使用示例：**

```java
@Autowired
private RedissonDataHandle dataHandle;

dataHandle.set("user:1001", "张三");
dataHandle.set("token:abc", "data", 30, TimeUnit.MINUTES);
String val = dataHandle.get("user:1001");  // "张三"
```

## 七、生命周期与事件机制

本模块不直接使用 Spring 事件机制，但通过以下方式与 Spring 生命周期交互：

| 阶段 | 触发点 | 说明 |
|------|--------|------|
| 容器初始化最早期 | `SpringUtil.initialize()` | `ApplicationContextInitializer` 回调，保存 `ApplicationContext` 引用 |
| 自动配置加载 | `RedissonCommonAutoConfiguration` | `@AutoConfigureBefore` 确保在官方配置前执行 |
| Bean 创建 | 4 个 `@Bean` 方法 | 按依赖顺序执行 |
| Bean 属性注入后 | `LocalLockCache.localLockCacheInit()` | `@PostConstruct` 构建 Caffeine 缓存 |

启动流程：

```
Spring Boot 启动
  → SpringUtil.initialize()                    ← ApplicationContextInitializer
  → AutoConfiguration.imports 发现本模块配置类
  → @AutoConfigureBefore 拦截官方 Redisson 配置
  → 创建 RedissonClient（依赖 RedisProperties）
  → 创建 RedissonDataHandle（依赖 RedissonClient）
  → 创建 LocalLockCache → @PostConstruct 初始化 Caffeine
  → 创建 LockInfoHandleFactory
```

## 八、性能优化策略

| 优化点 | 位置 | 策略 |
|--------|------|------|
| 条件创建线程池 | `RedissonCommonAutoConfiguration` | 仅在 `corePoolSize` + `maximumPoolSize` 同时配置时才创建，避免不必要开销 |
| 有界任务队列 | `RedissonCommonAutoConfiguration` | `LinkedBlockingQueue(256)` 防止 OOM |
| 原子线程命名 | `RedissonCommonAutoConfiguration` | `AtomicInteger` 无锁自增 |
| 参数名缓存 | `LocalVariableTableParameterNameDiscoverer` | `ConcurrentHashMap` 类级缓存，每个类只解析一次 |
| 本地锁缓存 | `LocalLockCache` | Caffeine 接近 `ConcurrentHashMap` 性能，`expireAfterWrite` 自动清理 |
| 锁实例原子创建 | `LocalLockCache` | `Caffeine.get(key, mappingFunction)` 保证无重复创建 |
| 连接快速失败 | `RedissonCommonAutoConfiguration` | `connectTimeout(1000)` 1 秒超时 |
