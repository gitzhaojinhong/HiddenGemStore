# 高效幂等组件

---

## 一、组件概述与定位

### 1.1 功能定位

`hgs-repeat-execute-limit-framework` 是一个基于 Redisson 的高性能幂等防护组件，旨在解决 Web 项目中请求重复执行的问题。与传统分布式锁方案不同，该组件针对幂等场景做了专门优化：

- **分布式锁**：多个不同用户的并发请求都要依次执行，最终全部完成
- **幂等组件**：同一用户的重复请求只需执行一次，其余直接拒绝

### 1.2 支持场景

- 用户 API 请求的重复提交防护
- MQ 消息的重复消费防护

### 1.3 技术栈依赖

| 依赖 | 用途 |
|------|------|
| `hgs-redisson-common-framework` | Redis 操作封装（RedissonDataHandle）、锁信息解析（AbstractLockInfoHandle）、本地锁缓存（LocalLockCache） |
| `hgs-service-lock-framework` | 分布式锁服务（ServiceLockFactory、ServiceLocker） |
| `spring-boot-starter-web` | Spring AOP 支持 |
| Redisson | Redis 分布式锁底层实现 |
| Caffeine | 本地高性能缓存，用于管理 JVM 级别的 ReentrantLock 实例 |

## 三、核心类逐一剖析

### 3.1 @RepeatExecuteLimit 注解

**文件**：`com.hiddengemstore.repeatexecutelimit.annotion.RepeatExecuteLimit`

```java
@Target(value = {ElementType.TYPE, ElementType.METHOD})
@Retention(value = RetentionPolicy.RUNTIME)
public @interface RepeatExecuteLimit {
    String name() default "";           // 业务名称
    String[] keys();                    // 幂等唯一标识（SpEL 表达式）
    long durationTime() default 0L;     // 幂等保持时间（毫秒）
    String message() default "提交频繁，请稍后重试";  // 提示信息
}
```

**设计要点**：
- `@Target` 同时支持 `TYPE`（类级别）和 `METHOD`（方法级别），增强了使用灵活性
- `keys` 属性无默认值，是必填项，确保每个幂等操作都有明确的唯一标识
- `durationTime` 默认为 0，表示不设置持久化幂等标识，仅靠锁机制防护并发
- 支持 SpEL 表达式（如 `#apiData.id`），可在运行时动态解析方法参数

### 3.2 RepeatExecuteLimitConstant 常量接口

**文件**：`com.hiddengemstore.repeatexecutelimit.constant.RepeatExecuteLimitConstant`

```java
public interface RepeatExecuteLimitConstant {
    String PREFIX_NAME = "repeat_flag";    // Redis 键前缀
    String SUCCESS_FLAG = "success";       // 成功标识值
}
```

使用接口定义常量是一种常见模式，但现代 Java 更推荐使用 `final class` 配合私有构造器来防止被实例化或实现。

### 3.3 RepeatExecuteLimitLockInfoHandle 锁名称处理器

**文件**：`com.hiddengemstore.handle.RepeatExecuteLimitLockInfoHandle`

```java
public class RepeatExecuteLimitLockInfoHandle extends AbstractLockInfoHandle {
    public static final String PREFIX_NAME = "REPEAT_EXECUTE_LIMIT";

    @Override
    protected String getLockPrefixName() {
        return PREFIX_NAME;
    }
}
```

**职责**：继承 `AbstractLockInfoHandle`，通过模板方法模式提供幂等组件的锁前缀名称 `REPEAT_EXECUTE_LIMIT`，使幂等锁与分布式锁的 Redis 键名互不冲突。

**锁名称生成规则**：
```
{应用前缀}-{锁类型前缀}:{业务名}:{key1}:{key2}
示例: hgs-REPEAT_EXECUTE_LIMIT:createOrder:userId123
```

### 3.4 RepeatExecuteLimitAutoConfiguration 自动装配

**文件**：`com.hiddengemstore.config.RepeatExecuteLimitAutoConfiguration`

```java
public class RepeatExecuteLimitAutoConfiguration {
    @Bean(LockInfoType.REPEAT_EXECUTE_LIMIT)
    public LockInfoHandle repeatExecuteLimitHandle() {
        return new RepeatExecuteLimitLockInfoHandle();
    }

    @Bean
    public RepeatExecuteLimitAspect repeatExecuteLimitAspect(
            LocalLockCache localLockCache,
            LockInfoHandleFactory lockInfoHandleFactory,
            ServiceLockFactory serviceLockFactory,
            RedissonDataHandle redissonDataHandle) {
        return new RepeatExecuteLimitAspect(lockInfoHandleFactory, serviceLockFactory, localLockCache, redissonDataHandle);
    }
}
```

**自动装配机制**：通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件注册，这是 Spring Boot 3.x 的标准方式。

**Bean 注册**：
1. `repeatExecuteLimitHandle`：以 `LockInfoType.REPEAT_EXECUTE_LIMIT`（值为 `"repeat_execute_limit"`）作为 Bean 名称注册，供 `LockInfoHandleFactory` 按类型查找
2. `repeatExecuteLimitAspect`：注册核心切面 Bean，注入所有依赖

### 3.5 RepeatExecuteLimitAspect 核心切面

**文件**：`com.hiddengemstore.repeatexecutelimit.aspect.RepeatExecuteLimitAspect`

这是组件的核心，实现了三层防护的幂等机制。

#### 3.5.1 类声明与依赖

```java
@Slf4j
@Aspect
@Order(-11)   // 必须在 ServiceLockAspect(@Order(-10)) 之前执行
@AllArgsConstructor
public class RepeatExecuteLimitAspect {
    private final LockInfoHandleFactory lockInfoHandleFactory;
    private final ServiceLockFactory serviceLockFactory;
    private final LocalLockCache localLockCache;
    private final RedissonDataHandle redissonDataHandle;
}
```

#### 3.5.2 执行流程（around 方法）

```
请求进入
  │
  ├── 步骤1: 读取注解配置 (durationTime, message)
  │
  ├── 步骤2: 生成唯一锁名称 (SpEL 解析)
  │     lockName = "{app}-REPEAT_EXECUTE_LIMIT:{name}:{keys}"
  │     repeatFlagName = "repeat_flag" + lockName
  │
  ├── 步骤3: 第一次 Redis 检查（快速失败）
  │     if (Redis.get(repeatFlagName) == "success") → 抛异常
  │
  ├── 步骤4: 获取本地锁（JVM 级别）
  │     ReentrantLock.tryLock() → 失败则抛异常
  │
  ├── 步骤5: 获取分布式锁（集群级别）
  │     ServiceLocker.tryLock(lockName, 0, SECONDS) → 失败则抛异常
  │
  ├── 步骤6: 第二次 Redis 检查（DCL 双重检查）
  │     if (Redis.get(repeatFlagName) == "success") → 抛异常
  │
  ├── 步骤7: 执行业务逻辑 joinPoint.proceed()
  │
  ├── 步骤8: 设置幂等标识（如果 durationTime > 0）
  │     Redis.set(repeatFlagName, "success", durationTime, MILLISECONDS)
  │
  ├── 步骤9: 释放分布式锁
  │
  └── 步骤11: 释放本地锁
```

#### 3.5.3 三层防护机制详解

| 层级 | 机制 | 作用域 | 性能 | 目的 |
|------|------|--------|------|------|
| 第一层 | Redis 幂等标识检查 | 集群全局 | 最快（已有标识直接拒绝） | 防止 MQ 重试等长时间间隔的重复请求 |
| 第二层 | 本地 ReentrantLock | 单 JVM | 极快（纯内存操作） | 拦截同一实例内的并发重复请求，减少分布式锁竞争 |
| 第三层 | Redisson 分布式锁 | 集群全局 | 较快（Redis 网络 IO） | 保证集群环境下同一时刻只有一个请求执行 |
| 第二次检查 | Redis 幂等标识 DCL | 集群全局 | 快 | 防止在获取分布式锁期间，其他实例已完成执行并设置了标识 |

## 四、依赖组件深度分析

### 4.1 AbstractLockInfoHandle（锁信息抽象类）

**路径**：`hgs-redisson-common-framework` 模块

**核心职责**：使用 SpEL 表达式解析方法参数，生成唯一的锁名称。

**设计模式**：模板方法模式
- `getLockPrefixName()`：抽象方法，由子类定义前缀
- `getLockName()`：模板方法，组装完整的锁名称
- `getRelKey()` → `getSpElKey()`：SpEL 表达式解析链

**SpEL 解析流程**：
1. 从 `JoinPoint` 获取 `MethodSignature`
2. 处理接口代理情况，获取实现类的真实方法
3. 创建 `MethodBasedEvaluationContext`，注入方法参数
4. 使用 `SpelExpressionParser` 解析表达式（如 `#apiData.id`）
5. 将解析结果转为字符串拼接到锁名中

### 4.2 LocalLockCache（本地锁缓存）

**路径**：`hgs-redisson-common-framework` 模块

```java
public class LocalLockCache {
    private Cache<String, ReentrantLock> localLockCache;

    @Value("${durationTime:48}")
    private Integer durationTime;  // 默认 48 小时

    @PostConstruct
    public void localLockCacheInit() {
        localLockCache = Caffeine.newBuilder()
                .expireAfterWrite(durationTime, TimeUnit.HOURS)
                .build();
    }

    public ReentrantLock getLock(String lockKey, boolean fair) {
        return localLockCache.get(lockKey, key -> new ReentrantLock(fair));
    }
}
```

**设计要点**：
- 使用 Caffeine 缓存管理 ReentrantLock 实例，避免 GC 压力
- 支持公平锁/非公平锁模式选择
- 基于写入时间过期策略，默认 48 小时后自动清除
- `CaffeineCache.get()` 本身是线程安全的，保证同一 lockKey 始终返回同一锁实例

### 4.3 RedissonDataHandle（Redis 数据操作）

**路径**：`hgs-redisson-common-framework` 模块

提供对 Redisson `RBucket` 的简化封装：

| 方法 | 功能 |
|------|------|
| `get(key)` | 获取字符串值 |
| `set(key, value)` | 设置永不过期的值 |
| `set(key, value, timeToLive, timeUnit)` | 设置带过期时间的值 |

`getDuration()` 方法的时间单位处理：支持 `MINUTES`、`HOURS`、`DAYS`，默认回退到 `SECONDS`。

### 4.4 ServiceLockFactory（分布式锁工厂）

**路径**：`hgs-service-lock-framework` 模块

```java
public ServiceLocker getLock(LockType lockType) {
    return switch (lockType) {
        case Fair -> manageLocker.getFairLocker();
        case Write -> manageLocker.getWriteLocker();
        case Read -> manageLocker.getReadLocker();
        default -> manageLocker.getReentrantLocker();
    };
}
```

支持四种锁类型：`Fair`（公平锁）、`Reentrant`（可重入锁）、`Read`（读锁）、`Write`（写锁）。

## 六、并发安全与性能分析

### 6.1 并发安全保证

#### 6.1.1 单 JVM 内并发

```
Thread-1 ──→ Redis检查(通过) ──→ 本地锁(获得) ──→ 分布式锁(获得) ──→ 执行业务
Thread-2 ──→ Redis检查(通过) ──→ 本地锁(失败) ──→ 抛异常结束
Thread-3 ──→ Redis检查(通过) ──→ 本地锁(失败) ──→ 抛异常结束
```

#### 6.1.2 多 JVM（集群）并发

```
JVM-1/Thread-1 ──→ Redis检查(通过) ──→ 本地锁(获得) ──→ 分布式锁(获得) ──→ DCL检查(通过) ──→ 执行业务
JVM-2/Thread-1 ──→ Redis检查(通过) ──→ 本地锁(获得) ──→ 分布式锁(等待)  ──→ ...
                                                                   ↓
                                                              JVM-1 执行完毕，设置标识，释放锁
                                                                   ↓
JVM-2/Thread-1 ──→ 分布式锁(获得) ──→ DCL检查(发现标识) ──→ 抛异常结束
```

#### 6.1.3 DCL（双重检查锁定）的必要性

第二次 Redis 检查是关键的安全保障。考虑以下时序：

```
时间线:
  T1: 请求A 获得分布式锁，开始执行业务
  T2: 请求B 通过第一次Redis检查（此时标识还未设置）
  T3: 请求B 获得本地锁，等待分布式锁
  T4: 请求A 执行完毕，设置幂等标识，释放分布式锁
  T5: 请求B 获得分布式锁
  T6: 请求B 执行第二次Redis检查 → 发现标识 → 拒绝执行 ✓
```

如果没有 DCL，请求 B 会在 T5 之后重复执行业务逻辑。

### 6.2 性能优化策略

#### 6.2.1 分层拦截的性能收益

假设场景：1 秒内 100 个重复请求，5 个服务实例

| 拦截层 | 拦截数量 | 说明 |
|--------|----------|------|
| Redis 幂等标识 | 0 | 首次请求无标识 |
| 本地锁 | ~95 个 | 每个实例拦截约 19 个请求 |
| 分布式锁 | 4 个 | 集群中 5 个实例各 1 个请求竞争 |
| 最终执行 | 1 个 | 只有 1 个请求真正执行业务 |

**性能对比**：

- 纯分布式锁方案：100 次 Redis 网络 IO + 100 次业务执行
- 幂等组件方案：100 次 Redis GET（快速检查）+ ~5 次分布式锁竞争 + 1 次业务执行

#### 6.2.2 本地锁的价值

本地锁的核心价值在于**将分布式锁的竞争从 N 个请求降低到 M 个实例**（N >> M）。纯内存操作的耗时约为 Redis 网络 IO 的 1/50 ~ 1/100。

### 7.2 与 ServiceLockAspect 的执行顺序

| 切面 | @Order | 职责 |
|------|--------|------|
| RepeatExecuteLimitAspect | -11 | 先执行，检查幂等标识，获取本地锁和分布式锁 |
| ServiceLockAspect | -10 | 后执行，处理业务级分布式锁 |

`@Order` 值越小优先级越高。幂等切面必须在分布式锁切面之前执行，确保：
1. 重复请求在到达业务锁之前就被拦截
2. 避免不必要的分布式锁获取操作

### 7.3 与 Spring 事务的交互

如果目标方法标注了 `@Transactional`，执行顺序为：
```
RepeatExecuteLimitAspect (@Order -11)
  → ServiceLockAspect (@Order -10)
    → TransactionInterceptor (@Order 默认 Integer.MAX_VALUE)
      → 业务方法
```

这种顺序保证了：先加锁再开事务，避免事务内长时间持锁导致的死锁风险。

## 八、设计模式总结

| 设计模式 | 应用位置 | 说明 |
|----------|----------|------|
| **模板方法模式** | `AbstractLockInfoHandle` | 定义锁名称生成算法骨架，子类提供前缀 |
| **工厂模式** | `ServiceLockFactory`、`LockInfoHandleFactory` | 根据类型创建/获取锁实例和处理器 |
| **策略模式** | `ServiceLocker` 接口的不同实现 | 可重入锁、公平锁、读锁、写锁等策略 |
| **代理/AOP 模式** | `RepeatExecuteLimitAspect` | 通过切面透明地为方法添加幂等功能 |
| **双重检查锁定（DCL）** | `RepeatExecuteLimitAspect.around()` | 两次 Redis 检查，防止并发竞态 |
| **缓存模式** | `LocalLockCache` | 使用 Caffeine 缓存管理锁实例 |
| **自动装配模式** | `RepeatExecuteLimitAutoConfiguration` | Spring Boot 自动配置 |
